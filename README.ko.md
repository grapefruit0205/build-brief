# Build Brief

[English](README.md) | 한국어

Build Brief는 명시적으로 호출한 소프트웨어 요청과 관련 저장소 맥락을 완전하고 승인에 묶인 개발자용 실행 계약으로 바꾸는 Codex 플러그인입니다. 개발자용 계약을 먼저 만들고, 같은 의미를 쉬운 자연어로 번역하고, 승인을 요청한 뒤 승인된 내용만 구현합니다.

이 플러그인은 아키텍처 패턴 선택기가 아닙니다. 사용자가 모듈러 모노리스, 마이크로서비스, 이벤트 드리븐, 배치, 함수형 중 하나를 고를 필요가 없습니다. 실제 요구 동작과 코드베이스에 필요한 소프트웨어 설계 언어를 도출하고 그 의미를 실행 가능한 작업으로 연결합니다.

## LLM이 이미 설계할 수 있는데 왜 사용하나요?

성능이 좋은 코딩 모델은 자연어만으로도 설계를 추론합니다. Build Brief가 모델에 새로운 지능을 추가하는 것은 아닙니다. 요구사항·불변 조건·호환성·실패 동작·인수인계가 중요한 작업에서 모델의 암묵적인 추론을 눈에 보이고, 검토·재사용할 수 있으며, 승인에 묶인 형태로 만듭니다.

기본 인터페이스는 계속 자연어입니다. 코드를 바꾸기 전에 완전한 설계와 실행 의미를 확인하고 승인하고 싶을 때만 Build Brief를 사용하세요.

## 동작 방식

```text
자연어 요청
  → Build Brief를 명시적으로 선택하거나 $build-brief 호출
  → 선택한 작업만 arm하고 나머지 작업은 fail-open 유지
  → 가장 좁은 관련 저장소 맥락 확인
  → 완전한 개발자용 실행 계약 작성
  → 같은 계약을 쉬운 자연어로 번역
  → 저장소 밖에 정확한 계약 digest를 stage
  → 파일을 수정하지 않고 두 표현을 보여준 뒤 승인 요청
  → 승인 후 stage한 계약과 동일한 계약만 pass
  → 승인된 계약만 구현하고 검증
  → 중요한 변경은 수정 계약을 다시 승인받은 뒤 진행
```

Build Brief를 명시적으로 선택한 뒤에는 표현이 달라도 같은 흐름을 사용합니다. `설계해줘`, `구현해줘`, `해줘`, “design it”, “build it”, “implement it”, “do it”과 다른 언어의 같은 의도는 모두 완전한 실행 계약을 만듭니다. Build Brief에 관한 질문은 실행 호출이 아니며, 작업이 크거나 아키텍처와 관련 있다는 이유만으로 자동 활성화하지 않습니다.

## 하나의 계약, 두 가지 표현

권위 있는 개발자용 실행 계약에는 다음 필드가 들어갑니다.

| 필드 | 역할 |
| --- | --- |
| `boundary` | 해당 동작을 소유한 기존 구성요소·데이터 소유자·외부 계약 |
| `invariants` | 반드시 유지해야 하는 관찰 가능한 요구사항 |
| `system_semantics` | 필요한 상태·소유권·흐름·시간·동시성·일관성·실패·보안·호환성·마이그레이션·운영 의미 |
| `plan` | 승인할 목표·범위·비범위·Top-down 접근 |
| `implementation` | 현재 코드와 시스템 경계에 대응시킨 구체적인 설계 |
| `phases` | 작업에 비례한 구현 구간 |
| `steps` | 각 구간 안의 순서 있는 변경 |
| `tasks` | 승인을 받는 구체적인 코드·테스트·설정·스키마·문서 단위 |
| `execution_order` | 의존성과 안전한 실행 순서 제약 |
| `minimality` | 재사용할 기존 구조와 중요한 추가 요소별 근거 |
| `proof` | 수용 조건과 집중 검증 |

`plain_language`는 이 전체 계약을 쉽게 설명한 내용입니다. 개발자용 계약에 없는 결정을 추가하거나 불변 조건·호환성 약속·실패 동작·구현 요소·작업·실행 제약을 숨길 수 없습니다.

여섯 실행 필드는 모두 필요하지만 서로 다른 역할을 하며 작업에 비례해야 합니다. 작은 변경은 필드마다 한 줄이면 충분할 수 있습니다. 필드가 있다는 이유로 파일 하나짜리 수정을 큰 프로젝트로 부풀리면 안 됩니다.

## 승인은 실제 경계입니다

- 최초 요청은 아직 보여주지 않은 계약에 대한 승인이 아닙니다.
- Build Brief는 개발자용 계약을 먼저 보여주고 쉬운 번역을 이어서 보여준 뒤 승인·수정·쉬운 재설명·취소 중 하나를 묻습니다.
- Hook은 계약 원문이 아니라 stage한 계약의 digest를 대상 저장소 밖에 기록합니다.
- 승인 후에는 stage한 계약과 완전히 동일한 계약만 Hook을 통과합니다.
- 구현은 승인된 동작·범위·아키텍처·의존성·스키마·공개 계약·실패 의미·작업·실행 제약 안에 머물러야 합니다.
- 중요한 변경은 수정 계약과 다시 만든 쉬운 설명을 보여주고 재승인받은 뒤 진행합니다.
- 승인된 경계와 작업 안에 이미 포함된 되돌리기 쉬운 세부 선택은 재승인할 필요가 없습니다.

Hook은 구조·순서·stage 계약과 pass 계약의 동일성을 강제합니다. 설계가 옳은지, 사람이 실제로 승인했는지, 모든 코드 변경이 의미상 계약에 맞는지는 증명하지 못합니다. Skill·저장소 근거·집중 검증·의미 grader·사용자 검토가 그 경계를 담당합니다.

## 최소 충분 설계

요구 동작과 불변 조건은 반드시 통과해야 하는 정확성 Gate입니다. 이를 만족한 후보 중 현재 시스템을 가장 많이 재사용하고 정당화된 설계 변화량이 가장 작은 해법을 선택합니다.

새 배포 단위, 저장소, 큐 또는 비동기 경계, 공개 계약, 프레임워크나 의존성, 추상화 계층, 설정 표면, 운영 구성요소에는 네 가지가 모두 필요합니다.

1. 현재 요구사항 또는 저장소 사실
2. 기존 구조가 부족하다는 근거
3. 추가 요소가 막는 구체적인 실패
4. 집중 검증 방법

가상의 미래 규모·재사용·조직과 유행하는 용어는 근거가 아닙니다. 필요한 동시성·안전성·호환성·실패 처리는 코드가 늘어난다는 이유만으로 과설계가 아닙니다.

## 예시

입력:

```text
$build-brief 주문 취소 기능을 설계부터 구현해줘. 중복 환불을 방지하고 기존 API 호환성을 유지해야 해.
```

Build Brief는 먼저 기존 취소 경로, 환불 저장, 결제 어댑터, API 계약을 추적합니다. 그다음 기존 API 동작을 유지하고 재시도나 동시 취소에도 두 번 환불되지 않게 하는 불변 조건을 세우고, 그 의미를 현재 시스템에 대응한 `implementation`, `phases`, `steps`, `tasks`, `plan`, `execution_order`와 호환성·재시도·동시성·실패 검증으로 연결한 Top-down 계약을 만듭니다.

이어 같은 내용을 쉽게 설명합니다. 예: “주문 취소는 기존 API를 그대로 사용합니다. 같은 취소가 재시도되거나 동시에 들어와도 환불은 한 번만 실행되어야 합니다. 기존 주문·결제 경로를 재사용하고 승인된 취소 코드와 검증만 변경하며, API 호환성과 중복 환불 사례를 테스트합니다.”

마지막으로 묻습니다.

> 이 실행 계약을 승인하시겠습니까? 승인하면 이 계약에 포함된 내용만 구현하겠습니다.

승인 전에는 프로젝트 파일을 변경하지 않습니다.

## GitHub에서 설치

플러그인 마켓플레이스를 지원하는 Codex와 `python3` 또는 Windows의 `py -3`로 실행할 수 있는 Python 3.10 이상이 필요합니다.

```bash
codex plugin marketplace add grapefruit0205/build-brief
codex plugin add build-brief@build-brief
```

설치 후 ChatGPT 데스크톱 앱을 다시 시작하세요. 안내가 나타나면 포함된 Build Brief Hook을 검토하고 신뢰하세요. Codex CLI에서는 `/hooks`로 확인할 수 있습니다. 설치 또는 Hook 변경 후에는 새 작업을 시작해야 현재 릴리스를 불러옵니다.

## 사용법

평소에는 Build Brief 없이 자연어를 그대로 사용하세요. 승인 흐름이 필요한 작업에서만 플러그인을 선택하거나 Skill을 명시적으로 호출합니다.

```text
$build-brief 기존 전체 환불 동작을 바꾸지 않으면서 레거시 결제 코드에 부분 환불을 추가해줘.
```

Build Brief는 관련 코드를 확인하고 완전한 계약과 쉬운 설명을 stage하여 보여준 뒤 멈춥니다. 검토 후 다음처럼 승인합니다.

```text
이 실행 계약을 승인해. 승인한 내용만 구현해줘.
```

다른 개발자에게 넘길 계약만 필요하고 코딩은 원하지 않으면 명시하면 됩니다. 여섯 필드를 포함한 전체 계약은 만들지만 프로젝트를 수정하지 않습니다.

```text
$build-brief 다른 개발자에게 넘길 완전한 실행 계약과 쉬운 설명을 작성해줘. 구현은 하지 마.
```

호출 뒤 제외하려면 자연스럽게 요청하세요.

```text
이번 작업은 Build Brief 없이 계속해줘.
```

선택적인 strict 모드는 사용자가 명시적으로 요청할 때만 세션 전체에 Gate를 적용합니다. Build Brief가 스스로 strict 모드를 켜지 않습니다.

hooks/build_brief_gate.py             로컬 수정 및 계약 동일성 안전망

이번 릴리스에는 MCP 서버, 앱 연결, 외부 API 호출, 자격 증명 요구사항, 외부 런타임 의존성이 없습니다. Hook 상태는 Codex가 제공하는 `PLUGIN_DATA`에 저장되며, 계약 원문이나 런타임 상태를 대상 저장소에 기록하지 않습니다.

## 검증과 평가

```bash
python3 /path/to/skill-creator/scripts/quick_validate.py skills/build-brief
python3 /path/to/plugin-creator/scripts/validate_plugin.py .
python3 -m unittest discover -s tests -v
```

`evals/golden-prompts.yaml`은 기대 동작을 정의하며 벤치마크 결과가 아닙니다. 제한된 A/B 실행기는 고정된 일회용 저장소에서 플러그인 없음, 명시 호출 Skill만 사용, 명시 호출 Skill과 Hook 사용 조건을 비교합니다. 의미 grader는 요구 동작 누락, 원치 않는 차단, 승인 전 구현, 쉬운 설명 불일치, 실행 필드 누락, 승인 계약 밖 변경을 hard fail로 처리한 뒤 정당화되지 않은 설계 변화량을 감점합니다.

기록된 v0.5.0 opt-out pilot은 이후 릴리스에서 수정된 원치 않는 차단 결함의 과거 근거입니다. 조건별 한 번만 실행한 결과이며 일반적인 성능 주장이 아닙니다.

## 현재 한계

명시적으로 선택하면 구현 전에 완전한 계약과 설명을 보여주므로 일반 자연어 코딩보다 시간과 토큰이 더 듭니다. 그래서 Build Brief는 opt-in이며 사용하지 않을 때는 fail-open입니다. Hook은 지원 대상 로컬 도구 호출마다 표준 라이브러리 Python 프로세스를 작게 실행하므로 도구별 지연이 조금 있습니다.

Hook은 지원되는 라이프사이클 수정 경로를 다루는 순서 안전망이지 보안 샌드박스가 아닙니다. 저장소에 없는 실제 법적 정책·운영 트래픽·조직 관행 등은 사용자의 입력이 필요합니다. 행동 A/B 평가와 의미 grader는 신뢰도를 높이지만 아키텍처가 절대적으로 옳다고 증명할 수는 없습니다.
