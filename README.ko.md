# Build Brief

[English](README.md) | 한국어

Build Brief는 명시적으로 호출한 소프트웨어 요구를 실제 상황에 필요한 최소 충분 개발용 Design Contract로 번역하는 작은 Codex 플러그인입니다. 같은 계약을 쉬운 자연어로 설명하고 사용자의 승인을 기다린 뒤 구현으로 넘깁니다. 선택된 작업에만 Hook을 arm하며, 호출하지 않으면 세션 컨텍스트를 추가하거나 작업을 차단하지 않습니다.

이 플러그인은 **아키텍처 패턴 선택기**가 아닙니다. 사용자에게 모듈러 모노리스, 마이크로서비스, 이벤트 드리븐, 배치 처리, 함수형 같은 용어 중 하나를 고르게 하지 않습니다. 요구사항과 실제 코드베이스를 읽고, 그 상황에 필요한 설계 의미만 동적으로 구성한 뒤 각각을 구체적인 구현 또는 검증 결과로 번역합니다.

## LLM이 이미 설계할 수 있는데 왜 사용하나요?

성능이 좋은 코딩 모델은 자연어만으로도 설계를 추론할 수 있습니다. Build Brief가 모델에 새로운 지능을 추가하는 것은 아닙니다. 대신 모호한 요구사항, 여러 개발자나 에이전트 사이의 전달, 놓치기 쉬운 불변 조건이 있는 작업에서 그 추론을 더 반복 가능하고 명시적이며 전달하기 좋은 형태로 만듭니다.

기본 인터페이스는 자연어입니다. 개발자나 코딩 에이전트가 반드시 지켜야 할 의미를 구현 전에 이해하고 승인하고 싶을 때 Build Brief를 사용하세요.

## 동작 방식

```text
자연어 요구
  → 현재 작업에 Build Brief를 명시적으로 선택
  → 가장 좁은 관련 저장소 맥락 확인
  → 호출된 현재 작업에만 Gate 준비
  → 최소 충분 개발용 Design Contract 작성
  → 같은 계약을 쉬운 자연어로 설명
  → 저장소를 수정하지 않고 사용자 승인 대기
  → 승인된 계약을 일반 코딩 워크플로에 전달
```

상황에 따라 상태 전이, 도메인 불변 조건, 계약, 동시성, 일관성, 실패 처리, 데이터 수명주기, 호환성, 보안, 관측성, 배포 전환, 완료 증거 같은 의미를 도출할 수 있습니다. 이는 닫힌 체크리스트가 아니라 열린 설계 언어입니다.

## 명시적 호출, 승인 가능한 설계

Build Brief는 opt-in 호출 방식을 사용합니다.

- **명시적 호출:** 구현 전에 개발용 Design Contract를 검토하고 승인하려면 플러그인을 선택하거나 `$build-brief`를 사용합니다.
- **암묵적 활성화 없음:** 요청이 크거나 모호하거나 아키텍처와 관련되어 있다는 이유만으로 Skill을 켜지 않습니다. 일반 자연어 작업은 모델의 기본 흐름을 사용합니다.
- **하나의 계약, 두 표현:** 권위 있는 개발용 계약과 그 의미를 그대로 옮긴 쉬운 자연어 설명을 함께 보여줍니다.
- **구현 전 승인:** 최초 구현 요청 자체를 설계 계약 승인으로 간주하지 않습니다. 두 표현을 보여준 뒤 멈추고 사용자의 승인을 기다립니다.
- **작업계획 생성 안 함:** Phase·번호가 붙은 Step·Task·작업 분해·실행 순서를 만들지 않습니다. 승인 후 일반 코딩 워크플로가 구현 계획을 담당합니다.
- **호출 범위 수정 안전망:** 명시적 활성화 뒤 Skill이 현재 작업을 arm합니다. 그러면 Hook이 쉬운 설명·소유 경계·불변 조건·시스템 의미·최소성 근거·완료 증거가 들어간 계약을 요구합니다.
- **즉시 opt-out:** 호출 뒤 사용자가 마음을 바꾸면 현재 작업을 해제하고 일반 흐름으로 계속합니다.
- **선택적 strict 모드:** 모든 지원 대상 수정 전에 계약을 원하는 사용자는 세션에 strict 모드를 켤 수 있습니다. Build Brief가 임의로 켜지는 않습니다.

호출된 작업에서는 코드, 테스트, 설정 또는 스키마를 변경하기 전에 구현 가능한 Design Contract를 완성합니다. 계약은 현재 시스템 경계, 관찰 가능한 불변 조건, 중요한 시스템 의미, 최소한으로 정당화된 설계 변화와 검증 조건을 고정합니다. 코딩 에이전트가 작업을 어떻게 나누거나 어떤 순서로 수행할지는 정하지 않습니다. 가벼운 라이프사이클 Hook은 Skill이 현재 작업을 arm한 뒤에만 수정 경계를 강제합니다.

쉬운 자연어 표현은 결과 소프트웨어가 무엇을 하는지, 중요한 안전장치가 왜 필요한지, 무엇이 그대로 유지되는지, 사용자가 승인하는 중요한 실패 동작이나 절충이 무엇인지 설명합니다. 용어는 쉽게 바꿀 수 있지만 개발용 계약에 없는 결정을 추가하거나 중요한 결과를 숨길 수 없습니다. 승인 대상은 개발용 계약이며, 쉬운 설명은 같은 계약을 이해할 수 있게 해줍니다.

이 게이트는 작업에 비례합니다. 요청한 변경에 중요한 설계를 고정할 뿐, 전체 시스템 아키텍처를 미리 얼려버리지 않습니다. 게이트 전에도 읽기 전용 탐색은 가능하며, 저장소 전체가 아니라 요청된 동작의 진입점부터 확인합니다.

## 최소 충분 설계

요구 동작과 중요한 불변 조건은 반드시 통과해야 하는 정확성 Gate입니다. 이를 통과한 후보 중에서 현재 시스템을 가장 많이 재사용하고 정당화된 설계 변화량이 가장 작은 해법을 선택합니다.

새 서비스, 저장소, 큐 또는 비동기 경계, 공개 계약, 프레임워크나 의존성, 추상화, 설정 표면, 운영 구성요소를 추가하려면 현재 필요, 기존 구조가 부족한 이유, 방지하는 실패, 집중 검증 방법을 제시해야 합니다. 가상의 미래 규모·재사용·조직과 아키텍처 용어 자체는 근거가 아닙니다. 설계를 작아 보이게 만들기 위해 필요한 동시성·안전성·호환성·실패 처리를 제거해서도 안 됩니다.

이 동작은 Build Brief의 Skill과 Hook 계약 자체에 포함됩니다. 사용하는 사람에게 별도의 정책 또는 메모리 플러그인은 필요하지 않습니다.

플러그인에는 `SessionStart` 또는 요청별 Context Hook이 없으므로 사용하지 않는 세션에는 Build Brief 정책 문장이 추가되지 않습니다. 로컬 PreToolUse 런타임은 아키텍처를 분석하지 않고 네트워크도 호출하지 않으며, 지원되는 읽기 전용 호출·제어 명령·수정 호출만 구분합니다. 명시적으로 arm된 작업이나 사용자가 선택한 strict 세션만 차단하고, 사용자가 제외를 원하면 `bypass`로 현재 작업을 즉시 해제합니다. 보조 reference 파일도 호출된 작업의 범위가 넓거나 동작이 명확하지 않을 때만 읽습니다.

## 예시

입력:

> 재고가 5개 아래로 내려가면 구매 담당자에게 한 번만 알려줘. 짧은 시간에 재고 변경이 여러 번 들어올 수도 있어.

플러그인은 단순히 “이벤트 드리븐과 멱등성을 사용하세요”라고 답해서는 안 됩니다. 모든 저재고 저장이 아니라 임계값 통과를 감지하고, 동시 변경에서도 중복 억제가 안전하도록 만들며, 알림 실패 동작을 정하고, 경계값과 경쟁 상태를 증명해야 한다는 설계 의무로 번역해야 합니다. 기존 재고·알림 경로를 재사용하고, 현재 증거로 그 경로가 불변 조건을 지킬 수 없을 때만 새 브로커나 서비스를 추가해야 합니다. 이 설계를 구현 체크리스트로 바꾸어서도 안 됩니다.

쉬운 설명은 다음과 같을 수 있습니다. “재고가 처음 5개 아래로 내려갈 때만 담당자에게 알립니다. 여러 재고 변경이 동시에 들어와도 알림은 한 번만 가야 하며, 기존 방식으로 이 보장을 할 수 없다는 증거가 없다면 현재 재고·알림 시스템을 그대로 사용합니다.” 그다음 대응하는 개발용 계약을 보여주고 승인을 요청합니다.

플러그인 마켓플레이스를 지원하는 Codex 버전과 `python3`(Windows에서는 `py -3`)로 실행할 수 있는 Python 3.10 이상이 필요합니다.

```bash
codex plugin marketplace add grapefruit0205/build-brief

```

설치 후 ChatGPT 데스크톱 앱을 다시 시작하고, 안내가 나타나면 포함된 Build Brief Hook을 검토·신뢰하세요. Codex CLI에서는 `/hooks`로 확인할 수 있습니다. Hook 정의가 바뀌면 다시 검토해야 합니다. 그다음 새 대화를 시작하세요.

## 사용법

평소 작업에는 자연어를 그대로 사용하세요. 구현 전에 Design Contract의 의미를 이해하고 승인하고 싶을 때만 Build Brief를 선택하거나 `$build-brief`를 호출합니다.

아키텍처 용어를 직접 고를 필요는 없습니다. 사용자는 “이번 작업에 검토·재사용 가능한 설계 계약이 필요한가?”만 판단하면 됩니다. 암묵적인 실패 의미가 중요한 변경, 호환성을 보존해야 하는 레거시 작업, 여러 경계를 건드리는 기능, 다른 사람이나 에이전트에게 넘길 작업이 대표적입니다.

호출한 뒤 마음을 바꾸면 자연스럽게 말하면 됩니다.

```text
이번 작업은 Build Brief 없이 일반 방식으로 바로 진행해줘.
```

현재 세션의 모든 지원 대상 수정에 Gate를 요구하려면 Build Brief를 명시적으로 호출해 strict 모드를 켜달라고 요청하세요.

구현 또는 변경 요청:

```text
$build-brief 기존 전체 환불 동작을 바꾸지 않으면서 레거시 결제 코드에 부분 환불을 추가해줘.
```

Build Brief는 관련 코드를 확인하고 쉬운 설명과 개발용 계약을 보여준 뒤 멈춥니다. 두 내용을 검토한 다음에만 계속합니다.

```text
이 Design Contract를 승인해. 구현을 계속해줘.
```

지시문만 작성:

```text
$build-brief 다른 개발자에게 넘길 개발용 Design Contract와 쉬운 설명만 작성해줘. 코딩하거나 작업 단계로 나누지는 마.
```

## 설계 원칙

- 사용자의 제품 의미, 범위, 권한을 보존합니다.
- 기존 저장소가 있다면 번역하기 전에 실제 코드를 확인합니다.
- 고정된 패턴 목록에서 고르지 않고 상황으로부터 설계 언어를 생성합니다.
- 모든 설계 용어를 구체적인 구현 또는 검증 결과에 연결합니다.
- 하나의 권위 있는 개발용 계약과 같은 의미의 쉬운 자연어 표현을 함께 제시합니다.
- 쉬운 설명이 아니라 개발용 계약을 승인 대상으로 삼습니다.
- Design Contract를 Phase·Step·Task·실행 순서로 대체하지 않습니다.
- 정확성을 필수 Gate로 두고, 통과한 후보 중 정당화된 설계 변화량이 가장 작은 해법을 선택합니다.
- 기존 구조를 재사용하고, 중요한 새 설계 요소마다 현재 증거를 요구합니다.
- Build Brief를 명시적으로 호출한 작업에서는 비례적인 Design Contract가 arm된 Gate를 통과하기 전에 구현 파일을 변경하지 않습니다.
- 명시적 제외 요청을 즉시 따르고, 사용자가 선택하지 않은 strict 모드를 임의로 켜지 않습니다.
- 가장 좁은 관련 증거부터 확인하고 중요한 미확정 동작이 있을 때만 탐색 범위를 넓힙니다.
- 계약을 보여준 뒤 승인을 기다리고, 승인된 계약을 일반 코딩 워크플로에 전달해 계획과 구현을 맡깁니다.
- 작은 변경은 작게 유지하고 설계 용어를 장식처럼 사용하지 않습니다.

## 검증

`evals/golden-prompts.yaml`에는 활성화되어야 하는 사례, 활성화되면 안 되는 사례, 경계 사례와 한국어 사례가 들어 있습니다. 각 사례는 재사용할 구조와 증거 없이 추가하면 안 되는 설계 요소도 정의합니다. 이 파일은 기대 동작과 의미 불변 조건을 정의하며, 측정된 벤치마크 결과를 주장하지 않습니다.

구조 검증:

```bash
python3 /path/to/skill-creator/scripts/quick_validate.py skills/build-brief
python3 /path/to/plugin-creator/scripts/validate_plugin.py .
python3 -m unittest discover -s tests -v
python3 evals/semantic_grader.py /path/to/assessment.json
```

행동 검증에서는 같은 대표 요청을 플러그인 없음, 명시적으로 호출한 Skill만 사용, 명시적으로 호출한 Skill과 Hook 사용 조건으로 실행합니다. 승인 우선 사례는 설계 미리보기 턴을 실행해 저장소가 바뀌지 않았음을 확인한 뒤, 같은 세션에 명시적 승인을 보내 구현을 재개합니다. 조건을 가린 모델 또는 사람 judge가 근거가 포함된 구조화 판단을 만들고, 결정적 grader가 정확성·원치 않는 차단·승인 전 구현·쉬운 설명의 불일치·작업계획 누출을 hard gate로 적용한 뒤 최소 충분 설계에 가장 큰 가중치를 둡니다. 활성화, opt-out, 시간, 토큰과 Hook 비용도 측정합니다.

첫 측정 pilot에서 v0.6.0의 원인이 된 v0.5.0 결함이 확인됐습니다. 고정된 실제 저장소의 opt-out 작업 1회에서 플러그인 없음과 Skill만 사용 조건은 100점이었지만, Skill+Hook은 한 번 차단하고 Design Contract를 요구해 0점이었습니다. [`evals/results/v0.5.0-opt-out-pilot.json`](evals/results/v0.5.0-opt-out-pilot.json)을 확인하세요. 조건별 1회 결과이므로 일반 벤치마크가 아닙니다.

## 현재 범위

Build Brief는 어떤 일반 작업이 아키텍처 우선 처리를 필요로 하는지 대신 결정하지 않습니다. 강한 코딩 모델은 플러그인 없이도 평소의 암묵적 설계를 계속 수행합니다. 명시적 호출은 추가 시간과 토큰을 사용하는 대신 눈에 보이고 이해 가능하며 승인할 수 있는 Design Contract와 수정 경계를 제공하며, 선택적 strict 모드는 사용자가 원할 때 세션 전체 강제를 제공합니다.

Mutation Gate는 arm된 작업 또는 사용자가 선택한 strict 모드에서 구조적으로 유효한 계약이 기록될 때까지 `apply_patch`와 보호 대상 Bash 명령 같은 지원되는 수정 경로를 차단합니다. 지원되는 읽기 전용 명령과 안전한 읽기 전용 파이프라인은 항상 허용합니다. 계약에는 `plain_language`, `boundary`, `invariants`, `system_semantics`, `minimality`, `proof`가 있어야 하며, `implementation`, `steps`, `phases`, `tasks` 같은 최상위 작업계획 필드는 거부됩니다. 다만 완전한 보안 경계는 아닙니다. Hook은 구조만 확인할 뿐 설계의 의미적 진실성이나 실제 사용자 승인 여부를 판정하지 않으며, 일부 특수 도구 경로는 Codex 라이프사이클 Hook을 통과하지 않을 수 있습니다. 이 보장은 Skill·저장소 증거·사용자 상호작용·행동 평가가 담당합니다. 반복되는 프롬프트 컨텍스트는 피하지만 지원 대상 로컬 도구를 호출할 때마다 표준 라이브러리만 사용하는 작은 Python 프로세스를 시작하므로, 명령 호출이 아주 많은 작업에는 도구별 지연이 조금 남습니다.
