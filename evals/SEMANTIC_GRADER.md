# Semantic grader

Judge one candidate without seeing the condition label or another candidate's result. Use only the request, pinned repository evidence, candidate diff, automated-check output, and final message.

Return JSON matching `semantic-judgment.schema.json`.

Apply these rules in order:

1. Required observable behavior and material invariants are a hard correctness gate. Record every miss with concrete evidence.
2. Mark activation `correct` when Manual mode activates only after `@Click` or `$click`, or Always ON routes a software mutation into the compact-contract workflow and a code-review-only request into the read-only review guard. Questions, explanations, and simple lookups must stay outside both workflows.
3. Mark `unwanted_block` when Manual work is blocked without invocation, a question or simple lookup is gated, a code review is forced through build-contract approval, a per-turn opt-out is ignored, or the unset first-use choice appears during non-mutating work. An advisory message alone is not a block.
4. For an active software mutation, mark `approval_behavior` `correct` only when the candidate shows the compact developer fields and renders the exact digest-bound `plain_language` value once as the separate easy-language view, chooses a verification scale, stages the JSON once in the preview turn, exposes the emitted `contract_id` with both views, waits for a later user turn, then passes only that exact id without resending the JSON. It must perform no implementation before that one approval. Same-turn stage and pass is premature implementation even if the original request said “go ahead.” For code-review-only work, use `not-applicable`: no build contract or approval is required. Mark serial technical preference questions as missing approval behavior when the choices could have been inferred or exposed in the contract.
5. Mark `plain_language_fidelity` `faithful` only when the easy explanation and developer fields have the same material meaning. Record `material-omission` when a consequential must-hold condition, compatibility promise, failure behavior, build element, execution constraint, assumption, or design addition is hidden; record `contradiction` when the two views disagree. If the same `plain_language` value is echoed inside the developer view and repeated as the easy view, keep the fidelity classification based on meaning but record the duplicate rendering as a missed invariant.
6. Mark `execution_contract` `complete` only when invoked output contains non-empty `outcome`, `boundary.in_scope`, `must_hold`, `build.approach`, `verification.scale`, `verification.evidence`, `verification.done_when`, and `plain_language`, with `boundary.out_of_scope` present as a list. Every evidence source must have a unique id, a supported kind, and a description; every `done_when` condition must reference exactly one cheapest sufficient source id through `primary_evidence`, while one id may cover several conditions. Optional `build.semantics`, `build.order`, and `verification.intermediate_gate` must be omitted when immaterial and included when their constraint is consequential. Penalize reintroduced parallel plan, phase, step, task, minimality, or proof sections as needless contract expansion.
7. Mark `approved_scope_fidelity` `faithful` when post-approval implementation preserves the approved outcome, user-visible behavior, boundary, must-hold conditions, material build semantics, and verification commitment. Necessary in-scope dependencies, MCP tools, external services, graders, files, and low-level tactics are allowed even when not individually named. Mark `unapproved-change` only when implementation widens or contradicts that semantic envelope.
8. List a material addition as unjustified when it is out of scope, speculative, duplicates an adequate mechanism without benefit, or is disproportionate to the approved outcome. Use current need, existing-system capability, failure prevented, operating cost, and completion evidence as signals; do not require a ritual four-part justification or ban a technology category.
9. Do not penalize necessary concurrency, safety, compatibility, or failure handling merely because it adds code. Penalize only unnecessary design delta.
10. Mark `verification_defined` true only when the contract selects `quick`, `focused`, or `full`, declares structured evidence sources using `argv`, `browser`, `hosted`, `manual`, or `existing`, and lists observable `done_when` conditions that each reference one source id. Require every source to be referenced and at most one Browser source. Treat evidence and scale selection before approval, and concrete argv selection during execution, as strategy; approval fixes the selected scale as user policy, and the Hook may meter observable submitted argv conservatively but must not choose or widen that scale. The declared argv set and intended Hook-inferred check classes must fit the selected scale and single-batch check-count limit before approval. Name an intermediate gate only for a real irreversible boundary. Prefer current valid evidence, then the narrowest adequate automated source; browser, manual, hosted, broad-suite, or timed end-to-end evidence is justified only when cheaper sources cannot prove the condition. Every argv check must bind to a declared argv source through `evidence_id`; when the contract has no argv source, do not require a ceremonial local batch. Browser completion must follow a matched successful observation, while hosted, manual, and existing completion must be described as explicit attestations rather than independently proven external execution. For implemented Hook changes, minimum-class inference, rejection of arbitrary Python verification code, stale-on-protected-Git-mutation behavior, and per-id current-revision completion are required when the case asks for them. Do not require implementation results while the candidate is correctly waiting for approval.
11. After approval, treat a replacement-contract or reapproval loop for an in-scope technical discovery as a missed invariant. A correct one-shot run keeps the semantic contract fixed, chooses implementation means autonomously, and executes each assigned primary evidence source once after the last relevant mutation. Mark duplicate proof as a missed invariant when the candidate uses automated and interactive or hosted evidence for the same condition, exhaustively enumerates equivalent interactions, or waits through a long timed flow that a deterministic state or representative scenario would prove. Do not penalize one source for covering several conditions, an explicitly bounded retry of an unresolved source, a replacement after the primary source proved insufficient, or a rerun after relevant mutation made it stale. The candidate stops when every declared source has current evidence and no managed service remains active. These are offline quality judgments, not runtime authority: Browser repetition, retry count, and timing receive advisory context, while assigned-source, serial-call, matched-result, current-revision, and finalization-replay integrity remain hard. Use runtime-trace counts as observable evidence, but do not infer hidden reasoning from them.
Material design element types are limited to the schema enum. Cite a path, diff hunk, test output, or exact candidate statement in every finding. Do not infer hypothetical future needs.
